# P5.1 — 物品能存在于世界上

## Context

P5 物品经济的第一步。玩家走进房间，地上有物品——这是整个物品交互链的起点。当前 EntityService 能创建 Entity 数据（纯 C#）+ 为角色生成 GO，但物品要出现在地面上有 3 个缺口：

1. **没有 GroundItem 组件** — 物品在世界上长什么样、有什么交互行为，没有代码
2. **EntityService 不可空 Prefab 阻断** — 10 件防具 Prefab 为空 → `LogError + return`，无法世界生成
3. **没有物品位置索引** — 不知道"哪个物品在哪个坐标"

## Reference: 成熟项目方案

本研究覆盖 5 款生存/建造游戏 + Unity 通用模式。核心结论：**所有项目在「数据之上薄视图」这个原则上完全一致**。

### 各游戏关键模式

**Project Zomboid — 地面物品的双向互斥模型**
- `InventoryItem` 要么在容器（`container != null`）要么在地上（`worldItem != null`），绝不两者同时
- 物品放置到地上：`square:AddWorldInventoryItem(item, x, y, z)` — 格块持有世界物品列表
- 物品拾取：移除 worldItem → `Destroy(IsoWorldInventoryObject)` → 加入玩家 `ItemContainer`
- **启示**：EntityService 的 Entity.View（GO 引用）已经是这个互斥模型的实现——有 View = 在地上，无 View = 在容器

**RimWorld — Maker→Spawn→SpawnSetup 三段式 + 自序列化**
- `ThingMaker.MakeThing(def)` → `GenSpawn.Spawn(thing, pos)` → `SpawnSetup(map)` 注册到空间索引
- 此流水线与 RedDust 的 `new Entity(id, preset)` → `Raise(SpawnRequest)` → `Identity.BindEntity` 完全同构
- **最关键模式**：`ExposeData()` — 每个 Thing/Comp 自己实现序列化，无集中序列化器。RedDust 的 PropertyTable 已为此设计——每个属性节点自带读写
- Tick 分层值得借鉴：地上物品不需要每帧 Tick，低频更新/事件驱动即可

**7 Days to Die — 基于区块的体素世界**
- 战利品容器是方块（`Class="Loot"`），物品在容器内而非直接在地上
- 玩家放置的容器永不生成战利品（硬编码规则）
- 区块重置（`MaxChunkAge`）清除未访问区域的修改
- **启示**：未来 P6+ 大世界阶段需要考虑区块化，但 P5.1 的小场景不需要——对象池足够

**Don't Starve — 组合式 ECS + 客户端/服务器分离**
- `SetPristine()` 之前：引擎层组件（Transform/AnimState/Physics）— 客户端+服务器
- `SetPristine()` 之后：游戏层组件（inventoryitem/stackable/weapon）— 仅服务器
- Tag 驱动行为：`inst:AddTag("sharp")` → `inst:HasTag(...)` 判断可用操作
- **启示**：RedDust 的 `Entity`(纯数据) vs `Identity+GroundItem`(GO 表现) 已经是此分离。GameplayTag 体系就是 Tag 驱动模式

**Factorio — 一切皆实体 + 传送带间距存储优化**
- `item-on-ground` 是与建筑、传送带同级的实体原型
- 最著名的优化：传送带物品存储**间距**而非绝对坐标——操作成本 O(1) 与物品数量无关
- Active entity 双向链表：零成本休眠，需要时唤醒
- **启示**：数据结构决定性能天花板。P5.1 场景物品数量有限（几十个），O(n) 线性扫描够用。大世界阶段再考虑空间哈希/网格优化

**Unity 通用模式 — ScriptableObject 定义 + 对象池**
- 三个独立层：数据（SO 定义 + 运行时状态）→ 逻辑（纯 C#）→ 视图（泛型 Prefab）
- 对象池是地面物品最重要的优化：**停用不销毁** — 拾取时 `SetActive(false)` 回池
- 双碰撞体：物理碰撞体接地 + 触发器碰撞体检测拾取（分离图层）
- **启示**：RedDust 的 `PropertyPresetSO`(定义) + `Entity`(运行时) + `GroundItem`(视图) 正在建立此三层分离。P5.1 先不做对象池——几十个物品不需要

### 对 RedDust 的三个核心启示

1. **数据之上的薄视图**：每个游戏都只有一个泛型 GroundItem 组件/实体，从共享的物品定义构建外观。我们的 `GroundItem.InitVisual(entity)` 就是这个模式。

2. **分布式持久化 > 集中式持久化**：RimWorld 的 ExposeData 和 Don't Starve 的 OnSave/OnLoad 都是组件自序列化。RedDust 的 PropertyTable 已经为此设计。

3. **小场景用池，大世界用区块**：P5.1-5.5 场景规模有限，简单 Dictionary 索引 + Unity ObjectPool（P5.2 拾取频繁时再加）足够。到 P6 建造系统的大世界阶段再引入区块流式加载。

## Recommended Approach

**最小可行路径**：GroundItem 组件 + EntityService 改两处 + GroundItem.prefab → 就能在屏幕上看到物品。

ItemService（L2 服务）在同一 PR 内创建但不阻塞视觉里程碑。

## Key Decisions

| 决策 | 理由 |
|------|------|
| EntityService 按 `preset is CharacterDefSO` 分流 | 角色沿用 Preset.Prefab，物品走 GroundItem.prefab → 改动最小，不耦合具体物品类型 |
| GroundItem 放 `L3_Identity/` 与 Identity 同目录 | Identity 回答"这是什么"，GroundItem 回答"这长什么样"——视觉互补，不新建模块 |
| fallback mesh 解决空 Prefab | 防具/null-Prefab 物品显示占位立方体而非报错——P5.1 要求"存在"不要求"好看" |
| ItemService 在同一 PR 但 Step 5 | P5.1c 视觉不需要它，但 P5.2 需要空间查询——建好不阻塞 |
| CharacterDefSO 仍走原有 Instantiate 路径 | 角色生成不改——降低风险 |
| LootSystem 不属于 P5.1 | 战利品表依赖地图+容器（Phase 6），P5.1-5.5 用手 spawn 测试物品足够 |

## Implementation Steps

### Step 1: GroundItem.cs（新建 L3 组件）

**File:** `Assets/Scripts/Services/Modules/L3_Identity/GroundItem.cs`

- `[RequireComponent(typeof(Identity))]` — GO 始终知道自己是哪个 Entity
- `InitVisual(Entity entity)` — 从 `entity.Preset.Prefab` Instantiate 3D 模型作为子物体，或显示 fallback Mesh
- `modelAnchor` Transform — 调整模型 pivot/scale
- 轻量——P5.2 再加交互相关字段（高亮、拾取半径）

### Step 2: EntityService.cs（修改两处）

**File:** `Assets/Scripts/Services/L2_EntityService/EntityService.cs`

**2a:** 加 `[SerializeField] private GameObject groundItemPrefab;`

**2b:** 替换 `OnSpawnRequest` 中的空 Prefab 阻断逻辑（当前 line 60-64）：

- `preset is CharacterDefSO` → 走原有路径（需 Prefab 非空）
- 其他 → `Instantiate(groundItemPrefab, ...)` → `Identity.BindEntity` → `GroundItem.InitVisual(entity)`
- 同样逻辑应用到第二分支（已有 Entity 生成 GO，line 88-122）

关键行为变化：非角色 Entity 不再要求 `Preset.Prefab != null`。

### Step 3: GroundItem.prefab（Unity Editor 手工创建）

**Asset:** `Assets/_Project/Prefabs/GroundItem.prefab`

结构：
```
GroundItem (root)
├── Identity (component)
├── GroundItem (component, modelAnchor → ModelAnchor)
├── SphereCollider (isTrigger, r≈0.5)
├── Rigidbody (kinematic)
└── ModelAnchor (child Transform)
    └── Fallback (MeshFilter=Cube + MeshRenderer=Gray)
```

创建后在 Inspector 中将此 Prefab 拖入 EntityService 的 `groundItemPrefab` 字段。

### Step 4: PlayerService 测试入口

**File:** `Assets/Scripts/Services/L2_PlayerService/PlayerService.cs`

在 `SpawnTestEntities()` 末尾加入测试代码：

```csharp
// P5.1 test: spawn consumable on ground near player
var beans = GameService.Instance.Assets.FindItem<ConsumableSO>("CannedBeans");
if (beans != null)
{
    var pos = playerStartAnchor.transform.position + Vector3.right * 2f + Vector3.up * 3f;
```

### Step 5: ItemService.cs（新建 L2 服务）

**File:** `Assets/Scripts/Services/L2_ItemService/ItemService.cs`

- 继承 `ModuleChildMono`
- `OnAssemble` → `GameContext.Instance.RegisterService(this)`
- `OnWire` → 订阅 `spawnedEvent` / `despawnedEvent`
- `_worldItemPositions: Dictionary<string, Vector3>` — EntityId → 世界坐标
- Public API: `SpawnWorldItem()`, `IsOnGround()`, `GetWorldPosition()`, `GetNearbyItems()`
- 过滤 `CharacterDefSO` — 只追踪世界物品

**目录:** `Assets/Scripts/Services/L2_ItemService/`

## Data Flow

```
Caller (ItemService.SpawnWorldItem 或直接 Raise):
  spawnRequestEvent.Raise(new SEntitySpawnRequest(preset, id, position))
    → EntityService.OnSpawnRequest
      → new Entity(id, preset)
      → Register(entity)
      → preset is CharacterDefSO?
          YES: Instantiate(preset.Prefab) [existing]
          NO:  Instantiate(groundItemPrefab)
      → Identity.BindEntity + SetProperties
      → GroundItem.InitVisual(entity)
      → entity.View = go
      → spawnedEvent.Raise(SEntitySpawned)
        → ItemService.OnEntitySpawned: 记录位置到 _worldItemPositions
```
