## 决策〇：脚本运行时选型

**结论：HybridCLR 社区版。用于内部开发热重载，不为 Mod 专属。**

### 为什么选 HybridCLR 而非 xLua

经四轮辩论 + 6 角度评议团审查。论证链：

| 轮次 | 核心结论 |
|------|---------|
| 初评 | Level 4 脚本 Mod "❌ 不做，不预留，不准备" |
| 6 席评议 | IL2CPP 下后期加脚本 ≈ 重写游戏 → "不堵门"优于"不准备" |
| 二辩（xLua 辩护） | xLua 解决的核心问题是团队协调瓶颈（策划等程序员），对独立开发者不成立 |
| 三辩（独立开发者视角） | 独立开发者最大风险是弃坑——双语言税 + 绑定层 + 跨语言调试消耗精神能量 |
| 四辩（HybridCLR 方案） | HybridCLR 消解了 xLua 的三个核心痛点：不需要学新语言、不需要维护绑定层、不需要跨语言调试 |

**xLua 在 2017-2020 年是唯一答案。2026 年不是了。**

| | xLua (Lua) | HybridCLR (C#) |
|---|---|---|
| 语言 | Lua（需额外学习） | C#（与项目同语言） |
| 绑定层 | 需要 C#↔Lua 桥接 | 不需要——Mod 直接调用 C# API |
| 调试 | 跨语言，栈分裂 | 同语言，统一调试器 |
| 热重载 | Lua 文件热替换 | IL 解释器动态加载 C# 程序集 |
| 维护状态 | 官方停滞（最后 release ~2021） | **非常活跃**（持续更新 Unity 6 兼容） |
| 未来兼容 | 需找社区 fork 适配 | CoreCLR Desktop 成熟后可平滑过渡 |

### 社区版 vs 商业版

RedDust 是单人存档游戏（非 MMO），玩家存档退出 → 重启 → 继续，全程 10 秒。社区版够用：

- **不需要运行时热修复**（商业版 Hotfix 的核心卖点）——改 C# 代码后重启的频率低（月均一两次），用户代价小
- **数值调整不需要重启**——PropertyDefSO 体系已是数据驱动，改数值走 Addressables 下发，玩家无感
- **把商业版的预算留给更需要的地方**

### 对 Mod 的影响

HybridCLR 的加载能力已在项目中（内部开发热重载用）。Release 版本**保留外部程序集加载能力**——这不是"加"一个功能，是"不关"一扇门。

## 决策一：Mod 深度边界

**结论：目标 2 级（效果组合），Level 4 🟡 不堵门。**

| 级别 | 内容 | 本次 |
|------|------|------|
| 0 — 数值调整 | 改伤害、耐久、掉落率 | ✅ S1 |
| 1 — 新增内容 | 新物品、新技能、新 NPC | ✅ S1 |
| 2 — 新增行为 | 新效果类型、新 Ability 逻辑 | 🎯 目标 |
| 3 — 表现层 | 新 UI、新动画、新模型 | 🔮 不封死 |
| 4 — 脚本 | C# 代码 Mod（通过 HybridCLR） | 🟡 不堵门 |

### Level 4："不堵门" ≠ "不做"

Release 版本 HybridCLR 加载门**开着**——Mod 作者可以写 C# Mod，但 API 标注 unstable。

| | ❌ 不做（原结论） | 🟡 不堵门（修正后） | ✅ 做（全承诺） |
|---|---|---|---|
| 加载外部 C# 程序集 | 关闭 | **开着**（零成本——HybridCLR 已在项目里） | 开着 |
| API 文档 | 无 | 内部注释即可 | 完整公开文档 + 教程 |
| API 稳定性承诺 | 无 | **pre-1.0, may change** | 1.0 即锁定 |
| 示例 C# Mod | 无 | dogfood 时自然产生 | 专门维护 |
| 工作量 | 零 | **零** | 显著（维护公共 SDK） |

**开着门 ≠ 承诺 API**。Mod 加载器的日志打一行 `"Mod API is pre-1.0 and unstable. Mods may break on updates."` 就够了。早期 Mod 作者（RimWorld 2013-2016 那群人）完全接受这个——他们是 co-creators，不是消费者。

### 三个"不堵门"动作（零实现成本）

1. **不 sealed 管道核心类**（`AbilityExecutor`、`AbilityReactor` 等）——保留继承扩展的可能性
2. **把级别 2 的效果组合系统设计好**——变量槽、条件分支、非战斗钩子这三个积木不仅服务 Mod 作者，也服务内部开发
3. **接受社区用 HybridCLR 写 C# Mod**——门开着，标注 unstable，不主动阻止

### 从 "不堵门" 到 "做" 的门槛

四个条件**全部满足**才考虑升级为正式承诺：

1. 核心循环已验证（100+ 陌生人留存数据）
2. 商业信号明确（Wishlist 5 万+ 或 EA 首两周回本）
3. Mod 社区已自然形成（有人自发用 HybridCLR 写 C# Mod）
4. 付费内容路线图饱满（已有 DLC 或明确计划）

**在此之前："把战斗手感调好比 API stability guarantee 重要 100 倍。"**

## 决策二：数据主权

**结论：全对象 Override。Mod 可以整个替换官方数据定义。**

- Mod 声明要覆盖的目标 ID → 该 ID 的整个数据对象被 Mod 版本替换
- 不是字段级合并（如"只改 damage"），而是整个对象替换
- 两个 Mod 都想覆盖同一个 ID → 加载顺序决定（后加载赢），冲突记入日志

**为什么不是字段级**：字段级合并固然灵活，但需要定义"哪些字段可独立覆盖"的 Schema——这是额外复杂度，且官方改了字段结构后 Mod 的部分覆盖可能语义错乱。全对象替换简单且语义清晰。

## 决策三：内容 ID 体系

**结论：纯字符串 + 自动命名空间前缀 + ID 废弃别名系统。**

```
官方内容:  "item.bandage", "entity.zombie.basic", "ability.slash"
Mod 内容:  用户在 JSON 写 "id": "sword"
          → 加载器根据 manifest author 自动解析为 "@authorId.sword"
```

**三条规则**：
1. **自动命名空间**：Mod 作者永远不需要手动写前缀。系统根据 Mod manifest 的 `author` 字段自动注入，保证 Mod 间零 ID 冲突
2. **点分层次**：官方 ID 采用 `category.subcategory.name` 命名约定（如 `item.weapon.melee.katana`）
3. **废弃别名**：官方重命名 ID 时保留旧 ID 作为 deprecated alias，Mod 引用不立即断裂。alias 在下一个 major version 时清理

**为什么不是 GUID**：GUID 在工程上最安全，但直接杀死"零代码门槛"——JSON 里全是乱码，Mod 创作者无法手写。字符串方案匹配 GDD 的核心承诺。

## 决策四：Mod 间互操作

**结论：允许硬依赖。**

- Mod manifest 的 `dependencies` 字段声明依赖的 Mod ID
- 加载器按依赖拓扑排序，检测到环 → 报错
- 缺失依赖 → 该 Mod 拒绝加载，提示玩家缺少什么
- 可选依赖（`optionalDependencies`）留到 S2 有社区反馈时补

**为什么允许依赖**：实现成本极低（拓扑排序 + 环检测），但生态价值高——可以有"基础框架 Mod"让别人在上面扩展，而非每个 Mod 都是孤岛。

---

## 决策五：加载时机

**结论：S1 启动时静态加载。Mod 变更需重启游戏。**

- 启动 → 扫描 Mods/ 文件夹 + Workshop 订阅目录 → 校验 → 构建完整数据表 → 进主菜单
- 改 Mod JSON → 重启游戏生效（Unity 重启 ~30s）

**为什么不是热重载**：静态加载实现最简单，数据一致性最强。S1 的 Mod 作者是早期 adopters（对重启容忍度高）。热重载在 S2 根据真实反馈迭代——届时创作者会说"重启太慢了"还是"完全无所谓"，用数据决策。

## 决策六：存档与 Mod 关系

**结论：警告 + 占位物品。**

- 存档记录创建时激活的 Mod 列表 + 版本号
- 读档时检测 Mod 变更（缺失/新增/版本变化）
- **Mod 物品缺失**：弹窗告知玩家缺少哪些 Mod，Mod 物品变为"损坏的遗物"（占位物品，不可用但保留在背包/世界中）
- **重新启用 Mod**：占位物品恢复为原始物品
- **Mod 更新**：物品属性即时生效（不锁定旧版属性）——和官方物品更新的行为一致

**为什么不是禁止加载**：玩家可能换电脑、Mod 被作者下架、Steam Cloud 没同步。禁止加载意味着丢存档——这会摧毁玩家对 Mod 的信任。

## 决策七：平台策略

**结论：Steam Workshop 首发。**

- S1 直接集成 Steamworks.NET，实现上传/订阅/更新
- 手动安装（Mods/ 文件夹）作为开发测试通道
- 非 Steam 平台（Epic/GOG）的 Mod 分发暂不在路线图中

**意味着**：Steamworks 集成是 S1 的核心工程项之一，不是"以后再说"的附加功能。

## 决策八：创作者工具链

**结论：S1 文档 + 示例。编辑器导出 S2 再看。**

S1 交付：
- Mod 创作教程文档（Markdown，覆盖"改数值""加武器""加技能""加 NPC""做依赖"5 个场景）
- 5 个可运行的示例 Mod（对应上面 5 个场景，有注释）
- Mod 清单格式规范 + JSON Schema 定义

S2 根据社区反馈评估：
- 策划编辑器加"导出为 Mod"按钮
- 或社区自己做了工具（像 RimWorld 那样）→ 官方不需要做

**原则**：文档是无论如何要写的。编辑器导出是产品功能（每个版本必须能用），不是"顺手加个按钮"。

## 决策九：内容治理

**结论：DMCA 流程，不主动审核。**

- Mod 使用协议（上传到 Workshop 时需同意）：禁止侵犯版权、禁止恶意代码、禁止 NSFW
- DMCA 侵权举报渠道：收到有效 DMCA 通知后下架
- 社区举报机制：玩家可举报违规 Mod，团队定期抽查
- 官方收编 Mod：以个案方式处理，与原作者协商（不在此阶段做制度设计）

## 决策十：分阶段投入

**结论：激进路线——S1 直接 Workshop 集成。**

```
S0: 地基（与 Mod 无关的基础设施）
├── 内容 ID 体系定稿 + 现有内容 ID 规范化
├── 存档格式的 Mod 引用字段设计
├── JSON Schema 定义（物品/实体/技能/配方/建筑）
└── HybridCLR 社区版接入（内部热重载用，非 Mod 专属）

S1: Workshop 首发（核心交付）
├── Mod 清单格式 + ModService 加载器（静态加载）
├── Steam Workshop 集成（上传/订阅/更新）
├── 游戏内 Mod 管理 UI（启用/禁用/排序/冲突提示）
├── 全对象 Override + 硬依赖 + 冲突检测与日志
├── 存档 Mod 变更检测 + 警告弹窗 + 占位物品
├── 效果组合系统（级别 2 的核心交付——变量槽/条件分支/非战斗钩子）
├── Release 版本 HybridCLR 加载门开启（标注 pre-1.0 unstable）
├── 5 个官方示例 Mod + 创作文档
└── DMCA/举报渠道（Workshop 页面配置）

S2: 深度（以社区反馈为门）
├── 编辑器导出按钮
├── 可选依赖 + Mod 合集
├── 冲突可视化（不只是日志，是 UI 展示）
├── 正式 Mod API 文档（如果社区已自然形成）
└── API 稳定性承诺（1.0 后逐步锁定）

S3: 表现层（以市场需求为门）
├── AssetBundle Mod（新模型/新动画/新 UI）
└── Total Conversion 支持
```

**S1 的规模**：核心增量来自两块——(1) Steamworks 集成从"S2 再说"变成 S1 核心交付；(2) HybridCLR 加载门在 Release 默认开启（零成本，但明确了 Level 4 策略）。如果 Mod 社区是核心差异化，半吊子上线不是差异化——RimWorld 的 Workshop 一键订阅 = 生态起飞的物理条件。HybridCLR 门开着 = 社区可以从 Day 1 探索 C# Mod 的可能性。
