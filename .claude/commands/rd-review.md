description: 多模型分层代码审查——Opus 深度逻辑审查 + 多 Haiku 交叉合规审查
argument-hint: [path | 默认所有待提交改动]
allowed-tools: Read, Write, Edit, Glob, Bash, Grep, Agent, Skill
---

对代码改动执行多模型分层审查：用一个高级推理模型（Opus）做深度逻辑审查，再用至少三个轻量模型（Haiku）从不同角度做合规交叉验证。

---

## 一、确定审查范围

| 用户输入 | 范围 |
|----------|------|
| 未指定路径 | `git diff HEAD` — 所有待提交改动（staged + unstaged） |
| 指定文件/目录 | `git diff HEAD -- <path>` |
| 指定 commit | `git diff <commit>..HEAD` 或 `git diff <base>..<head>` |
| 与 master 比较 | `git diff master..HEAD` |

第一步输出审查范围的摘要（文件列表 + 改动行数统计）。

---

## 二、Phase 1：Opus 深度逻辑审查

用 **Opus** 模型启动一个 Agent，对 diff 做深度逻辑审查。审查维度：

| 维度 | 关注点 |
|------|--------|
| **正确性** | 逻辑错误、边界条件遗漏、空引用风险、类型误用 |
| **数据流** | 数据传递方向是否符合自上而下、有无反向查询 |
| **并发/时序** | Awake/Start/OnWire 调用顺序、事件注册/注销配对 |
| **资源管理** | Unity 对象生命周期、内存泄漏、资源加载卸载对称 |
| **边界情况** | 空集合、极值输入、状态切换中的操作 |

Agent prompt 要点：
- 传入完整 diff 内容
- 要求输出结构化结果：文件 + 行号 + 严重级别（🔴严重/🟡警告/🔵建议）+ 描述
- 每条结论必须有 diff 中的具体代码引用
- 标注不确定的推断（"可能存在"vs"确认存在"）

同时启动 Phase 2（二者独立，并行执行）。

---

## 三、Phase 2：Haiku 合规交叉审查

用 **三个 Haiku** Agent（角度 A/B/C 必选，角度 D 条件追加）从不同合规角度并行审查同一份 diff。

### 角度 A：代码约定合规

审查依据（通过 Skill 工具加载 `rd-conventions`）：
- 命名规范 — 英文标识符、风格统一、功能表达清晰
- 拆分原则 — 单次改动是否过于庞大、是否一个文件做太多事
- 迭代原则 — 是否一次提交塞入过多不相关的功能块

### 角度 B：架构原则合规

审查依据（来自 CLAUDE.md + rd-conventions 架构节）：
- 数据自上而下 — 有无反向查询 GameContext
- 父调子不跨级 — 有无跨模块层级调用
- 统一写入入口 — CharacterRig 是否唯一物理写入点
- PropertyDef Min/Max 边界 — 业务公式有无重复 clamp
- Edit vs Write — 修改 .cs 是否用了 Edit 而非 Write

### 角度 C：NPE Guard 审查 ⚠️ 重点

**核心原则**：不在业务代码中检查空值（[[non-null-principle]]）。配置和初始化在构造时完成，基础设施层内部 guard。**禁止暴露空值检查为公共 API。**

审查双重任务：

**🔴 反模式检测（不该加的 NPE Guard）**：
| 反模式 | 示例 | 危害 |
|--------|------|------|
| 静默吞空 | `if (x == null) return;` | 掩盖初始化 bug，让错误在下游更远处爆炸 |
| 业务代码 guard | 方法体内 `_data?.DoSomething()` | 表明初始化不完整，应该在上游 fix 而非下游兜 |
| 公共 API 暴露空检查 | `public bool IsValid() => _ref != null;` | 把内部状态泄露为 API 契约 |
| 重复 guard | 上游已保证非空，下游又检查一次 | 代码膨胀，模糊真正的契约边界 |
| `??` 默认值掩盖 | `var v = _config?.Value ?? 0f;` | 配置缺失被静默替换为 0，数值 bug 极难排查 |

**🟢 必要 Guard 识别（应该加但可能缺失的）**：
| 场景 | 判断标准 |
|------|----------|
| 用户输入 / 外部数据 | 网络消息、存档反序列化、配置文件读取 → 需要 guard |
| Unity SerializeField | Inspector 中可能未赋值 → Awake/Start 中 assert 而非静默跳过 |
| 跨模块边界 | 从其他模块接收的数据 → 模块入口 guard + 明确错误信息 |
| `GetComponent` / `FindObject` | 运行时查找可能失败 → 必须检查并明确报错 |
| 可选功能/组件 | 设计上就是可选的 → 允许 null，但要显式标注 `// optional` |

**审查输出格式**：
每条发现必须标注类别：
- `[反模式-静默吞空]` / `[反模式-业务guard]` / `[反模式-API暴露]` / `[反模式-重复guard]` / `[反模式-??掩盖]`
- `[缺失Guard-外部输入]` / `[缺失Guard-SerializeField]` / `[缺失Guard-跨模块]` / `[缺失Guard-运行时查找]`

### 角度 D（条件追加，≥3 文件改动时启动）：Unity 最佳实践

- SerializeField 序列化是否正确
- MonoBehaviour 生命周期方法使用是否合规
- Prefab/Scene 引用是否安全

### 交叉验证规则

1. 将 Opus 报告和所有 Haiku 报告的发现按文件+行号归并
2. 同一问题被 **Opus + ≥1 Haiku** 发现 → ✅ 多方一致
3. 同一问题仅被 **单一 agent** 发现 → ⚠ 分歧，建议人工复核
4. Haiku 之间的分歧（角度 A 发现但角度 B 未发现）→ 注明角度差异，不视为矛盾
5. 如果 Opus 标记为 🔴严重 但无任何 Haiku 发现 → 高亮提醒
6. **NPE Guard 特殊规则**：
   - 角度 C 的 `[反模式-*]` 发现与角度 A（非空原则）交叉印证 → 置信度极高
   - 角度 C 的 `[缺失Guard-*]` 发现需与 Opus 的边界情况分析交叉对照
   - Opus 报告中的空引用风险 + 角度 C 标记 `[反模式]` 同一行 → **严重冲突**，该行同时存在"可能 NPE"和"不该加 guard"，说明初始化设计有结构性问题

## 五、调用方式

```
/rd-review                  → 审查所有待提交改动
/rd-review path/to/file.cs  → 审查指定文件
/rd-review master..HEAD      → 审查当前分支相对 master 的所有改动
```

---

## 六、注意事项

- Phase 1 和 Phase 2 同时启动，互相独立
- Phase 2 内部的角度 A/B/C 三个 Haiku Agent 同时启动，互相独立；角度 D 在 ≥3 文件时追加
- Opus Agent 的 diff 可以传完整内容；Haiku Agent 如果 diff 过大（>500 行），只传文件列表 + 关键代码段
- 角度 C（NPE Guard）的 Haiku Agent 必须加载 `rd-conventions` 和 memory 中的 [[non-null-principle]]
- 如果 diff 为空，退出并提示"无待审查改动"
- 报告直接输出到对话，不写入文件
- 如果用户追加 `--fix`，则对 ✅多方一致 的 🔴严重 问题自动修复（需逐项确认）
- **NPE Guard 反模式不得自动修复**——静默吞空的 guard 可能是刻意掩盖未解决的初始化 bug，移除前必须人工确认
